# traits.build (development version)

- A `traits` entry in `metadata.yml` can now list the values a contributor used to mean "no value" for that trait, in the new optional field `omit_values`: `omit_values: 0`, say, or `omit_values: ["-", "NaN"]`. The build treats them as missing, exactly as `custom_R_code` applying `na_if()` to the trait's column does, so swapping one for the other builds an identical database; it applies them after `custom_R_code` and before `substitutions`, and in long-format data only to that trait's rows. Values are compared with the column as `data.csv` was read: in a numeric column as numbers, so `0` also omits `0.0`, and in any other column as exact text, where an unquoted number is compared as R writes it (`0.0` as `0`), so quote it (`"0.0"`) to match its spelling. `dataset_test()` checks that the field is a string or number or a list of them, and `metadata_add_traits()` keeps it on existing traits. Nothing writes the field by default. Verified on `austraits.build`: moving the `na_if()` calls of all 58 datasets that use one into `omit_values` leaves 56 building identical databases, and the other two pass the result of `na_if()` on to further code (#12).

# traits.build 2.2.0

- New `dataset_check_duplicate_values()` lists values in a compiled database that may duplicate data already in another dataset, for a curator to review rather than as a test. Numeric values match when they agree at the precision of the less precise one, however a halfway value was rounded, and within `max_distance_km` when both have coordinates; categorical values only when identical, georeferenced and nearby. Results are summarised per pair of datasets -- the proportion of shared taxon x trait combinations that match, how many observations match on several traits, and how often each value occurs by chance across the trait -- with the records behind each match, their locations and contexts. Run it for one dataset or for every pair in the database; a full sweep of AusTraits takes about 15 seconds.
- A dataset whose `collection_date` column is not written as `yyyy-mm-dd`, `yyyy-mm` or `yyyy` can now declare the format it is written in, with `collection_date_format` in the `dataset` block of `metadata.yml` — `dmy`, say, or `dmy my y` for a column mixing full dates, month-year values and bare years. The build converts the column to the standard after `custom_R_code` runs. A column of timestamps, such as `2022-06-03T14:00:00Z`, also needs `collection_date_timezone`, since that instant is 3 June in UTC but 4 June in Sydney. A value is never guessed at: one that does not match the declared format is left as it is. `collection_date_format: auto` works the format out from the whole column instead, choosing between `dmy my y`, `mdy my y` and `ymd ym y`; where more than one reads the column and they give different dates, as for a column of `4/07/2022`-style values, it converts nothing and `dataset_test()` names the formats to choose between. Ranges of years written with a hyphen, `2019-2020`, become `2019/2020`. The same conversion is exported as `util_format_collection_date()`, for `custom_R_code` that needs standard dates before combining columns.
- `dataset_test()` now reports `collection_date` values that are not standard, checked on the built dataset so it sees what the database will hold. Accepted are `yyyy-mm-dd`, `yyyy-mm` and `yyyy` dates that exist and fall between 1700 and today, ranges of two of these separated by `/` whose start is not after their end. A date written `unknown/yyyy` or `.na/yyyy`, with an unknown start, is stored as the year alone, `yyyy`; the build makes that change as it processes the dates, so `metadata.yml` and `data.csv` can keep either form.

- `dataset_report()` gained `show_questions`. The default, `TRUE`, gives the review copy sent to a data contributor; `FALSE` gives a final copy for distribution, leaving out every question, the end-of-report question list, and the text that only explains them.
- In the dataset report, the identifiers table now has one row per identifier declared in `metadata.yml`, with its own record count, rather than one row pasting every `var_in`, `identifier_type` and `institution_code` together. The numeric trait plots now include `mode` values, previously dropped (about 12,500 observations across AusTraits), and the question asking for individual-level measurements when a dataset is mostly means is removed.
- `dataset_replace_disallowed_chars()` now also rewrites EM SPACE as a space, the `ﬁ` ligature (from PDF text extraction) as `fi`, and INCREMENT (`∆`, which Option-J types on a Mac) as GREEK CAPITAL LETTER DELTA, and deletes SOFT HYPHEN, which marks only where a word may wrap. The schema allows GREEK SMALL and CAPITAL LETTER DELTA (`δ`13C, `Δ`T).
- `process_parse_data()` no longer errors (`bind_cols()`: "Can't recycle ... to match ... (size 0)") when every dataset-level field it imports (`collection_date`, `basis_of_record`, `life_stage`, `measurement_remarks`, `source_id`, ...) is read from a data column rather than given as a fixed value; previously such a dataset could not be built.
- `dataset_test()` now accepts a context scoped to specific traits whose values are read from a data column rather than a fixed literal — a `traits` entry can set a field naming a column of `data.csv` (e.g. `leaf_temp: LfT_Rdark`, read per record), the same way `process_parse_data()` and `process_format_contexts()` already read it. Previously only a literal value (e.g. `method_context: 250 mm branch`) passed: `dataset_test()`'s context-consistency check compared the column's actual per-record values against the field's own declared value — the column name itself, never resolved against the data — which could never match, and any dataset using this pattern (already built correctly) failed validation with a confusing "context values ... not present in metadata" error. A blank cell in that column is a record with no value for the context, as it is for a `var_in` naming a column directly (#276).
- New `dataset_find_pivot_duplicates()` returns the rows behind `dataset_test()`'s "`traits` table cannot pivot wider" failure. It builds each dataset exactly as `dataset_test()` does and shares that check's definition of a duplicate, so the two always agree. `check_pivot_duplicates()` run on a compiled database could report nothing for a failing dataset, because `austraits::bind_databases()` drops rows identical in every column; the new function flags those rows with `exact_duplicate`.
- New `metadata_dewrap_fields()` rejoins text pasted into `metadata.yml` with the source's hard line breaks -- typically `sampling_strategy` and `methods` copied from a PDF or Word document -- which leaves continuation lines YAML reads as new keys, so the file fails to parse. At a line ending in a hyphen it keeps the hyphen and joins the next line without a space, since a word split by the wrap (`collec-tion`) cannot be told from a compound (`oven-dried`); `dehyphenate = TRUE` removes the hyphen where it splits a lowercase word instead, and the preview lists every such join. It single-quotes a joined value that needs it (e.g. one containing `": "` or `" #"`), and rewrites only those lines rather than reflowing the file through `write_metadata()`. `custom_R_code` is always copied through verbatim, since its line breaks are intentional. It previews by default; pass `dry_run = FALSE` to write.
- The data-model build in `ontology/` has a workflow: `make ontology` builds, `make ontology-check` validates and tests, `make ontology-site` renders and publishes into `docs/ontology/`, `make ontology-release` snapshots a version, and a CI workflow runs the first three on every pull request touching `ontology/`. The single 300-line script is now functions in `ontology/R/` and scripts in `ontology/scripts/`, mirroring the APD's build. The data-model version is the newest heading in the new `ontology/NEWS.md` rather than a hand-edited `params` block in `index.qmd`, and the page reads the schema from `inst/support/` rather than from whichever traits.build happened to be installed. `ontology/R/validate.R` checks the inputs (every `prefix:identifier` reference resolves, keys are unique, every matched namespace has a Turtle prefix) and the outputs (statements parse and none is dropped), with a register of the defects already in the published RDF so that only new breakage fails; `ontology/tests/testthat/test-golden.R` rebuilds into a temporary directory and compares against the committed artefacts byte for byte. The build no longer ends by calling `pkgdown::build_site()`, which was failing on `develop` and was the step whose omission left the published model a release behind (#275).
- Data model release 1.2.0, published at <https://w3id.org/traits.build> (#275, #276, #277). The site had been serving 1.0.0 since June 2025, although 1.1.0 (the `identifiers` table terms) had been built by #210. 1.2.0 matches the model to SOSA/SSN and the TERN Ontology, to the Darwin Core 2026-05-26 `MeasurementOrFact` and `Assertion` terms, and to the ETS terms for `value_type` and `basis_of_value`, and fixes defects in the published RDF. 74 external classes added; 2,054 to 2,467 statements. `ontology/NEWS.md` lists every change.
- `dataset_test()` now accepts `value_type` and `basis_of_value` in a dataset's `dataset` block, as the default for every trait that does not declare its own. The build has always honoured them there, but `dataset_test()` rejected them as invalid `dataset` fields and still demanded both on every trait, so metadata that built correctly failed validation (#249). A trait now needs only the fields its dataset block does not supply, and a value set on a trait still takes precedence over the dataset's.
- `dataset_test()` now reads every config file from `path_config`. The step that builds each dataset read `config/traits.yml`, `config/metadata.yml`, `config/unit_conversions.csv` and `config/taxon_list.csv` regardless of it, so a run from any other directory failed every dataset at "building dataset". Those files are also now read once per run rather than once per dataset (#129).
- `dataset_test()` no longer slows down in proportion to a dataset's number of locations. It ran a separate expectation for every location to check it had coordinates, and each expectation costs a few milliseconds, so `AVH_2026` in `austraits.build`, with 162,469 locations, took 507 seconds and ran 162,746 expectations. It now finds the locations that fail first and tests only those, taking that dataset to 39 seconds. The report is unchanged, verified line for line against 29 `austraits.build` datasets (#129).
- `dataset_test()` now runs on testthat's third edition, like the rest of the package, rather than switching back to the second for `context()`, which the third deprecates. Its report is unchanged apart from a `Testing dataset_test` header, verified against 29 `austraits.build` datasets. It can now also be run under a reporter that collects results rather than printing them, such as `testthat::ListReporter`, which previously aborted with `attempt to use zero-length variable name` (#234).
- The dataset report template is now `inst/support/report_dataset.qmd`, replacing `report_dataset.Rmd`. `dataset_report()` renders it with `quarto::quarto_render()` rather than `rmarkdown::render()`, so building reports now needs the Quarto CLI (`quarto` R package, in Suggests). Because Quarto always renders by shelling out to that CLI, which does its own `library(traits.build)`, report rendering now depends on what is *installed*, not on `devtools::load_all()` -- edit the plotting functions or the template and reinstall before re-rendering to see the change. `austraits` is written to a temp `.rds` and passed to the template by path rather than through Quarto's YAML-based `execute_params`, which cannot represent R's `NA` and cannot hold an object this large.
- `plot_categorical_trait_distribution()`, `plot_trait_distribution_jitter()` and `plot_trait_distribution()` (which dispatches to whichever of the two suits the trait) are now exported, so a dataset report's plots are functions of `traits.build` rather than living only inside the report template. `plot_trait_distribution_jitter()` needs `cli` (now in Suggests) in addition to the `forcats`, `ggplot2` and `scales` already there.
- `new_taxa_trait_combinations()` is renamed `dataset_new_taxa_trait_combinations()` and is now exported, so it can be reached without `:::`. By default it reads `database$taxa` rather than needing APCalign `resources`, so the "what did this dataset add" report works in `ausinvertraits.build` and `AusFizz`, not just `austraits.build`. It gained a `resources` argument: pass APCalign resources to judge which names are accepted against the current APC rather than the database's taxon list, which may be out of date. It also no longer drops accepted varieties and forms, which it filtered on as `varietas` and `forma` -- spellings neither APC nor the taxa table uses.
- A context populated by literals set on the metadata `traits` entries no longer has to spell out a `values:` list. Omitting `values:` derives the context values from whatever `var_in` names, and that now covers both of the ways a `var_in` is legitimately satisfied: a column of `data.csv`, or a field set on the `traits` entries naming no column at all (`var_in: method_context` and friends). Previously only the first was, so the second read a `data.csv` column that was never meant to exist and aborted with `rlang_error_data_pronoun_not_found`, naming neither the dataset, the `context_property` nor the `var_in` (#268). Descriptions are still hand-written. A `var_in` matching neither is still rejected, and the message now lists both the columns and the `traits` fields available rather than reading as though a column were the only option.
- A dataset may now keep its locations in a csv file beside `metadata.yml` rather than listing them in it, by setting `locations` to the file's name — `locations: locations.csv`. The file holds one row per location, a `location_name` column and one further column per location property, which is the shape `metadata_add_locations()` is given and the shape `austraits$locations` pivots to. This is for datasets compiled from per-record georeferenced occurrences, which generate one location per record: `AVH_2026` in `austraits.build` has 162,469 of them, making `metadata.yml` 487,518 lines and 17.7 MB, which is neither reviewable nor diffable. Holding them in a csv takes that file to 111 lines, and the dataset's `dataset_configure()` plus `dataset_process()` from about 16 minutes to 17 seconds (#263). Both forms build the same database, and inline `locations:` blocks are unaffected — nothing needs to be converted.
- In a locations csv, an empty cell means the location does not record that property, and `.na` means it is recorded but unknown — the same two states an inline `locations:` block distinguishes by listing a property or not. `metadata_add_locations()` gained a `file` argument for writing this form, and suggests it for a dataset with more than 1000 locations. `build_setup_pipeline()` declares the csv as a dependency of the dataset's `remake` and `targets` targets, so editing it triggers a rebuild.
- `dataset_test()` now decides whether a dataset has locations the same way the build does, from the formatted locations table rather than from `names(metadata$locations)`. The two disagreed for a dataset whose entire `locations:` block held a single property, where `dataset_test()` would join against an empty table that the build had already discarded.
- Reading a `metadata.yml` with a very large `locations:` block is no longer the dominant cost of building a dataset. `yaml::read_yaml()` costs roughly O(n^2) in the number of container nodes a document holds rather than in its size, so a dataset that generates one location per georeferenced record parses far slower than the trait data it describes: `AVH_2026` in `austraits.build`, with 162,469 locations, took 911 seconds to read (#263). `read_metadata()` now parses a large `locations:` block in chunks, which brings that file down to 1.8 seconds and the whole dataset's `dataset_configure()` plus `dataset_process()` from about 16 minutes to 46 seconds. Every chunk still goes through the same YAML parser, and anything unexpected about a file's structure falls back to parsing it whole, so no file is read differently than before — verified against all 574 `metadata.yml` files in `austraits.build` and `ausinvertraits.build`.
- `build_setup_pipeline()` gained `method = "targets"`, which writes a `_targets.R` pipeline. Like `remake` it caches, so editing one dataset rebuilds that dataset rather than all of them — on a 40-dataset compilation a cold build is 33.5s, a rebuild after changing one `data.csv` is 6.9s, and a run with nothing changed is 0.9s. Unlike `remake` it is on CRAN and maintained, and unlike `furrr` it does not rebuild everything. It caches on target *values*, so a metadata edit that does not change a dataset's output stops propagating there rather than rebuilding the compilation. Passing `workers` greater than 1 declares a `crew` controller and builds datasets in parallel. Where `qs2` is installed the pipeline stores its targets with it rather than as gzipped rds, which is internal to `targets` and leaves the exported `.rds` that consumers read unchanged; on that 40-dataset compilation the two together take a cold build to 24.6s and a one-dataset rebuild to 3.6s. The exported `.rds` is not written by `tar_make()` at all: it is around a third of a rebuild and is a publishing step rather than part of checking a dataset, so `build_export()` writes it when it is wanted. That takes a one-dataset rebuild to 2.2s, against 154s for a full build of `austraits.build`. Verified to produce a database equal to the one `method = "base"` produces (#17). Building from `_targets.R` is three steps rather than one, because `tar_make()` neither returns the database nor writes the export, so `build_setup_pipeline()` now names all three — including the `targets::tar_read()` that loads the result — using the `database_name` actually in use, and the generated `_targets.R` says the same at the top. `build_export()` called with a `database_name` the pipeline does not have now explains that the name must match the one the pipeline was set up with, rather than reporting only `target database not found`.
- `dataset_test()` no longer aborts with `the condition has length > 1` for a dataset that declares more than one identifier. `metadata$identifiers` is a list, so `is.na()` on it returns one value per identifier.
- Builds are now reproducible across machines. `observation_id`, `location_id` and the context ids were generated by sorting with `sort()` and `as.factor()`, which collate according to the session's `LC_COLLATE`. The same dataset therefore produced different ids on a contributor's machine than on CI, which runs in the C locale (#29). Ids are now always generated using C-locale collation, matching what previous builds produced on CI, so existing outputs are unchanged. `util_separate_and_sort()` is likewise no longer locale-dependent.
- `process_format_identifiers()` no longer fails with `object 'schema' not found`. Its third argument is the schema, as documented, rather than the trait data, and it now reads the identifiers list it is passed instead of looking one level too deep. `dataset_test()` was erroring on every dataset that declares identifiers.
- A context whose `var_in` names a column that isn't there is now reported as such, naming the dataset, the `context_property` and the missing column, and suggesting the nearest column name. It previously aborted with ``Assigned data `xxx[context_cols[[v]]]` must be compatible with existing data``, which named none of the three and read as a data-length problem rather than a typo (#247). A `var_in` that names a field on the metadata `traits` entries rather than a column of `data.csv` — `var_in: method_context` and friends — is still accepted, as is one created by `custom_R_code`.
- `metadata_add_contexts()` no longer writes time-valued contexts as a number of seconds (`9:00:00` became `32400.0`) when called with `user_responses`, and now reports when a time column has been reformatted so the recorded values can be recognised as matching `data.csv` (#49).
- `metadata_add_contexts()`, `metadata_add_traits()` and `metadata_add_identifiers()` now guess column types from the same number of rows as the build (`guess_max = 100000`), so a sparse column can no longer be typed one way when metadata is written and another way when the database is built.
- `metadata_add_source_doi()` now reports clearly that the optional `rcrossref` package is needed, and offers to install it in interactive sessions, instead of failing with `there is no package called 'rcrossref'` (#178).
- Corrected the link to the AusTraits source repository, which had been misspelled `autraits.build` in `DESCRIPTION`, the package documentation and `NEWS.md`, and pointed at a URL that did not resolve. The Code of Conduct and reference website links in `README.md` were also dead or redirecting, and now resolve directly.
- Added `CITATION.cff` and `inst/CITATION`, so `citation("traits.build")` and GitHub's "Cite this repository" widget both return the Wenk et al. (2024) paper. `CITATION.cff` is excluded from the package tarball via `.Rbuildignore`.
- Removed a duplicated "AusTraits family" section from `README.md`, which had been added twice.

# traits.build 1.0.0

This is the first major release of the {traits.build} package, providing a workflow to harmonise trait data from diverse sources. The code was originally built to support AusTraits (see Falster et al 2021, <doi:10.1038/s41597-021-01006-6>, <https://github.com/traitecoevo/austraits.build>) and has been generalised here to support construction of other trait databases. Detailed instructions are available at

- package website: <https://traitecoevo.github.io/traits.build/>
- package book: <https://traitecoevo.github.io/traits.build-book/>
